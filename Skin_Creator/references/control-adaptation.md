# Accepted background through export

Read this module only after the background has been accepted. Keep accepted images, geometry and overlay values unchanged while adapting controls.

When the user requests a new background after controls are configured, `preview --stage background --retain-controls true` shows retained styles and decorations alongside the new artwork. It remains a background preview, grants no acceptance and cannot authorize export; the new background still needs the user's acceptance.

For small raster badges, register each PNG with `decal --slot <id> --input <image>`, then use `decals` in custom colors. Each selected scene region accepts at most eight `{asset,width,placement,offset,opacity}` items; `asset` is the registered `assets/decal-<id>.png`, width is 8–256 CSS pixels and offset is `[horizontal,vertical]`. Alternatively use `{symbol,color,accent,...}` instead of `asset` for independent `A`, `B`, `X`, `Y`, `up`, `down`, `left` or `right` enamel keys. Four corner anchors use nonnegative offsets up to 512; `top-center`/`bottom-center` use a signed horizontal offset within ±512. The renderer preserves aspect ratio and pointer passthrough above the scene shade. Spread individual keys through safe empty spaces, then verify real hits. Image and unified-scene backgrounds remain intact; old `ornaments` stay supported. These data fields require an updated runtime.

Reuse explicit user colors, text and borders. Otherwise offer extracted-theme colors or custom colors; extraction uses `palette-ui` with four or five real multiselect checkboxes, followed by `palette-read`. Do not select on the user's behalf. Explicit custom styles use `colors --input ...`; the command reference defines `style`, `regionStyles` and `hover`.

Use per-region `surfaceOpacity` for translucent backgrounds; never dim the whole text container. Restrained built-in `ornaments` can decorate selected non-image controls. Keep badges near safe corners, outside native window buttons. Opacity settings are generated from the exported manifest; verify those options survive export and preserve per-Skin overrides. Use a runtime supporting any new ornament pattern.

Decide where color improves the interface. `regionStyles.<region>:null` retains native appearance; `surface:null` with explicit text gives a transparent surface. A scene-image region cannot be overwritten as a control. In separate mode only chat/sidebar are image regions; selected title bars, navigation and page headers can be independently styled. These control choices must not change accepted artwork.

Light backgrounds need dark neutral text/icons; dark backgrounds need light neutral text/icons. Explicit foreground requests do not authorize secretly changing the selected surface color. Contrast conflicts must be resolved visibly. Preserve code syntax, diff colors, status colors and multicolor semantic indicators. A global descendant text or SVG override is not an acceptable fix.

Apply `preview --stage complete`, then inspect native states relevant to the chosen scope: input focus, attachment button/menu, model controls, summary/popover inner backplate and normal dialogs. Open these without submitting, uploading or changing business data. Run `contrast --slot <state>` for each relevant opened state. Reports contain styles and geometry only; neutral text requires 4.5:1, monochrome icons 3:1 over a resolvable solid background. Mapped semantic meters, multicolor graphics, image backgrounds, disabled/hidden states and truncation remain explicit limits, never automatic passes. A meter remains semantic when its current status is gray; its separate ordinary symbol is still checked. Do not enter protected password contents for contrast inspection.

For a topbar seam, use `diagnose --slot titlebar`; check solid, gradient and shared-image paths. Do not enlarge native buttons or dragging regions to cover a decorative gap. For an apparent color cast, compare the final composite with the source before assuming decoder or renderer failure. Consult the matching recovery case and retain actual verification.

Ask for complete-result acceptance only after known theme failures are resolved. Record the actual acceptance of the exact revision, then `export --output <new-folder>`. The result contains only the validated manifest and referenced images. Keep prompts, source paths, raw reports, recovery history and screenshots private. Never overwrite installed/built-in folders through export.

`restore` ends the temporary preview and restores the prior Skin without changing saved pack/preferences data. If the runtime changed, use the normal owned-helper update path before reapplying the preview; do not force-restart the client or leave two companion processes fighting different revisions. Report excluded/unobserved states, shell-only coverage and real-client validation limits in delivery.

Semantic inspection mappings belong to Creator's `runtime/adapters/authoring-controls-<profile>.json`, selected by the exact inventory version in `runtime/adapters/versions.json`. Changing inspection rules invalidates cached contrast results, not the user's unchanged visual/background acceptance; `status.completeContrast.stale` exposes this. Re-audit the actual complete preview before export. These inspection-only changes do not require restarting the rendering helper. A client-version change does require a fresh inventory and matching renderer; never relabel old coverage as new-version evidence.

For a same-version control-selector correction, retain the previous adapter JSON and use `refresh-adapter`. Only proven unchanged geometry and non-selector configuration permit partial reuse; affected states and old region samples are invalidated and must be recaptured. Source art and palette stay intact, while stage acceptance must be re-established from genuine consent and equivalent background output. Inline Markdown may use a native span rather than a code element; inspect the actual markup before widening a selector.
